Sanabil Messages - Technical Architecture Report

Date: January 18, 2026

Project: Sanabil Messages

1. Executive Overview

Sanabil Messages is a specialized communication platform designed to bridge the gap between Sanabil Schools and parents. Unlike generic messaging apps (like WhatsApp), it provides a unidirectional, high-priority channel for critical school updates such as Absence Alerts, Exam Schedules, and Fee Notifications directly to the parent's device.

Core Value Proposition:

  • Guaranteed Delivery: Uses a dedicated Push Notification pipeline to ensure messages are seen.
  • Security: Strict "Allowlist" authentication ensures only registered parents can log in.
  • Persistence: all messages are stored permanently in the database, meaning history is never lost even if notifications are dismissed.

2. System Architecture

The system follows a Hub-and-Spoke architecture with three main pillars:

Backend (Db) ⬅️ ➡️ Dispatcher (Python) ➡️ Cloud (Expo) ➡️ Mobile App

The Three Pillars:

  1. The Database (Supabase): The "Source of Truth". It holds Student data, Parent allowlists, and the Message Queue.
  2. The Mobile App (React Native): The user interface. It handles Registration, Token Management, and displaying the Inbox.
  3. The Dispatcher (Python): The "Postman". A backend service that connects the Database to the Push Notification Cloud ("The bridge").

3. How It Works (Internal Logic)

The system operates on two critical workflows:

Workflow A: Device Registration (The "Handshake")

Before a parent can receive messages, the system must "know" their device.

  • Login: User enters phone number (e.g., +252...).
  • Verification: The App checks the 'allowed_parents' table. If allowed, an OTP is verified.
  • Token Generation: The App calls the operating system to get a unique digital address called a Push Token.
  • Sync: The App saves this token to the 'user_devices' table in the database, linking it to that specific parent.

Workflow B: Message Delivery (The "Pipeline")

When the school sends a message (e.g., "Absence Alert"):

  • Queueing: The message is inserted into the 'message_recipients' table with status 'pending'.
  • Dispatcher Loop: The Python script wakes up every 5 seconds and asks the DB: "Any pending messages?"
  • Processing: If a message is found, the Dispatcher looks up the active Push Token for that parent.
  • Dispatch: The Dispatcher sends the payload to the Expo Push API (Cloud).
  • Completion: The Dispatcher marks the message as 'sent' in the database (to prevent duplicates).

4. Key Components & Code Logic

A. The Dispatcher (push_dispatcher.py)

This is the most critical backend component. It automates the delivery process so the school admin panel never freezes while sending thousands of messages. It decouples the "Sending" action from the "Delivery" action.

B. Mobile Logic (notifications.ts)

This component manages integration with Android/iOS. Crucially, it includes Simulation Logic: it detects if the app is running in a Simulator (Expo Go) or a Real Device (APK) and adjusts the token generation accordingly to prevent crashes.

C. The Inbox (inbox.tsx)

The main dashboard. It queries the database directly. This ensures that even if a Push Notification is missed, the message data is always available in the list (Offline-First approach).

"Sanabil Messages is not just a chat app; it is a Broadcast Infrastructure. We built it with a 'Guaranteed Delivery' mindset. By separating the Mobile App from the Dispatching Logic, we ensure that the system can scale to thousands of parents. The architecture relies on robust cloud standards to ensure reliability and security."
